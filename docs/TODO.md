- [x] **Scénarios de dossier (la spec est le test)** — spec exécutable écrite par l'utilisateur, structurée en use cases Cockburn, avant l'implémentation (rouge/vert)
    - Documents use cases (Cockburn léger : acteur, niveau, précondition, scénario principal en étapes, extensions numérotées, garantie de succès) dans `docs/usecases/`, écrits et possédés par l'utilisateur ; chaque extension = un fichier scénario séparé, la couverture des extensions est comptable
    - Format de scénario : `given (dossier + état) / étapes (action + attendu à chaque étape) / expect final` ; répétitions pliées en une ligne (« appuyer sur → (x2) ») ; les voyages complets depuis l'accueil (lancement → dossier → tri → suppression) restent le territoire de la recette manuelle, pas des scénarios

    - Langage d'état codifié sur un sous-ensemble observable de `State` (écran, photo courante, statut, comptes du scan) : tout mot pointe vers un champ réel ou une fonction dérivée explicite, sinon il n'a rien à faire en scénario
    - Factorisation par préconditions : ensemble fermé et documenté d'états de départ reconnus (accueil, organisation, tri, confirmation) — l'interpréteur refuse un `given` hors de cet ensemble, un nouvel état de départ est une décision explicite
    - Miroir « tout état promis est un état produit » : chaque état de départ reconnu doit apparaître comme état final (`attendu`) d'au moins un scénario — contrôle CI ; un état promis non produit est un chaînon manquant nommé, pas découvert au moment d'un bug
    - Invariant « même état, quel que soit le chemin » : si plusieurs scénarios produisent le même état nommé (ex. « tri, photo courante P1 » après ouverture fraîche ET après organisation), leurs projections doivent être identiques — à l'écriture, l'`attendu` du scénario « organiser » porte les comptes du scan (`organisés: 1`), et la donnée périmée (`à organiser: 1`) fait tomber le rouge avant même l'implémentation ; état de départ reconnu « tri post-organisation » (prélude rejouant l'organisation) — c'est exactement le bug du scan périmé après organisation (2026-10-24), invisible des tests unitaires qui nourrissent chaque branche d'un état cohérent construit à la main
    - Complétude = somme de trois contrôles CI : extensions de use cases couvertes / couverture de code par les scénarios **seuls** sur `update` + Core / miroir des états de départ
    - Refactoring « modèle de vue » : décisions comportementales de présentation (bouton grisé, statut en erreur) dans des fonctions pures `State → sémantique`, la vue ne garde que le mapping sémantique → pixels
